# Візуалізація навчального матеріалу

Формат схем залежить від того, **чим учень читає**. Спершу з'ясуй це, потім вибирай.

## Крок 1 — визнач середовище читання

Порядок перевірки:

1. **`learner-profile.md`, поле `редактор:`** — головне джерело. Читай його першим.
2. Якщо поля немає — швидка перевірка: змінна `TERM_PROGRAM=vscode`, або `code --version`
   виконується успішно.
3. Якщо й це не дало відповіді — **запитай учня одним рядком** і запропонуй записати в профіль:

   > «Чим читатимеш матеріали — VS Code, чи щось інше (GitHub, телефон, Obsidian, браузер)?
   > Від цього залежить формат схем. Запишу в профіль, більше не питатиму.»

## Крок 2 — вибери гілку

| Середовище | Схеми в `.md` | Додатково |
|---|---|---|
| **VS Code** | `mermaid`-діаграми, як і раніше — плагін `Markdown Preview Mermaid Support` їх рендерить | нічого не треба |
| **Будь-що інше** | **списки, таблиці, нумеровані кроки** за патернами нижче | запропонуй HTML-супутник (див. кінець файлу) |
| **Невідомо** | списки й таблиці — безпечний дефолт | — |

Не роби обидва формати в одному файлі. Дві копії однієї схеми розійдуться при першій же правці.

# Патерни для не-VS-Code гілки

**Правило №0 — переносимість.** Файл мають відкрити в GitHub, на телефоні, у Блокноті,
в Obsidian, у чужому редакторі без плагінів. Тому схеми — це **вкладені списки,
таблиці й нумеровані кроки**, а не розмітка, яку треба чимось рендерити.

**Правило №1:** візуалізуй **матеріал**, не питання. Показуй концепції, процеси, зв'язки —
не «який JOIN вибрати».

**Правило №2:** одна схема = одна ідея. Два процеси — дві схеми.

**Правило №3:** текст українською, крім технічних назв (`SELECT`, `JOIN`, `HTTP GET`).

**Правило №4:** якщо схема не читається як список — вона занадто складна для файлу.
Спрости її або винеси в HTML-супутник (секція в кінці).

## 1. Карта теми — вкладений список зі статусами

**Коли:** на початку `plan.md` (обов'язково) і на початку великого блоку в `learn.md`.
Учень бачить усе поле однією прокруткою і розуміє, **чого він не знає**.

Статуси обов'язкові: ✅ розкрито · 🔜 відкладено з причиною · ❌ поза скоупом з причиною.

```markdown
## Мапа теми

- **Основи** ✅
  - `SELECT`, `WHERE`, `ORDER BY`
  - Типи даних і `NULL`
- **JOIN-и** ✅
  - `INNER`, `LEFT`, `RIGHT`, `FULL`
  - Декартів добуток — типова помилка
- **Агрегація** ✅
  - `GROUP BY`, `HAVING`, віконні функції
- **Індекси** 🔜 — після основ; без розуміння планів запиту вивчиться як магія
- **Транзакції та ACID** 🔜 — окремий блок, бо тягне за собою рівні ізоляції
- **Шардинг і реплікація** ❌ — поза скоупом: це вже адміністрування, не мова запитів
```

Чому список, а не картинка: учень може **скопіювати рядок** у пошук, ctrl+F по темі,
і побачити те саме на телефоні дорогою.

## 2. Процес або ланцюжок — нумеровані кроки зі стрілками

**Коли:** життєвий цикл запиту, порядок виконання, ланцюжок рішень.

```markdown
## Що відбувається при `SELECT`

1. **Парсер** — розбирає текст запиту → синтаксичне дерево
   ↓
2. **Планувальник** — рахує вартість варіантів → обирає план
   ↓ (тут вирішується: seq scan чи index scan)
3. **Виконавець** — читає сторінки з диска або кешу
   ↓
4. **Результат** — рядки повертаються клієнту

**Де ламається:** крок 2. Якщо статистика застаріла, планувальник обере seq scan
на таблиці з індексом. Лікується `ANALYZE`.
```

Розгалуження — вкладеним списком, не стрілками врізнобіч:

```markdown
3. Виконавець читає дані
   - якщо сторінка **в кеші** → віддає одразу
   - якщо **немає в кеші** → читає з диска, кладе в кеш, віддає
```

## 3. Взаємодія систем у часі — таблиця кроків

**Коли:** HTTP-обмін, auth flow, WebSocket, черга повідомлень.
Замінює `sequenceDiagram` і читається навіть краще, бо є колонка «що піде не так».

```markdown
| # | Хто → Кому | Що передає | Що піде не так |
|---|---|---|---|
| 1 | Браузер → API | `POST /login` з паролем | пароль у логах, якщо не вимкнути body-logging |
| 2 | API → БД | пошук користувача за email | timing attack: різний час для «немає юзера» і «пароль не той» |
| 3 | API → Браузер | `Set-Cookie` з JWT | без `HttpOnly` — токен вкраде будь-який XSS |
| 4 | Браузер → API | наступний запит із cookie | без `SameSite` — CSRF |
```

## 4. Стани — таблиця переходів

**Коли:** статус замовлення, життєвий цикл сесії, стани транзакції.

```markdown
| Поточний стан | Подія | Наступний стан | Примітка |
|---|---|---|---|
| `created` | оплата пройшла | `paid` | ідемпотентність: повторний webhook не має створювати другий перехід |
| `created` | таймаут 30 хв | `expired` | звільняє резерв товару |
| `paid` | відправлено | `shipped` | тут летить лист покупцю |
| `paid` | повернення | `refunded` | єдиний стан, з якого можна повернути гроші |
| `shipped` | — | — | кінцевий стан, переходів немає |
```

## 5. Зв'язки сутностей — таблиця замість ER-діаграми

```markdown
| Сутність | Поле-звʼязок | З чим повʼязана | Кратність |
|---|---|---|---|
| `Order` | `customer_id` | `Customer` | багато замовлень → один клієнт |
| `Order` | — | `OrderItem` | одне замовлення → багато позицій |
| `OrderItem` | `product_id` | `Product` | багато позицій → один товар |
```

Колонка «Кратність» — словами, не значками `||--o{`. Учень має прочитати вголос
і зрозуміти, а не розшифровувати нотацію.

## 6. Порівняння варіантів — таблиця критеріїв

**Обов'язкова**, коли в матеріалі є вибір (лінза 2 канону: жодної безальтернативної поради).

```markdown
| Критерій | Kafka | RabbitMQ | Коли що |
|---|---|---|---|
| Модель | лог із оффсетами | черга з підтвердженнями | треба перечитати історію → Kafka |

```

## 7. ASCII-схема — тільки коли структура справді просторова

Дозволена, коли важливе саме розташування: memory layout, дерево, топологія.
Тримай вузькою — до ~60 символів, інакше на телефоні поламається перенесенням.

```
        [Client]
            |
      [Load Balancer]
       /           \
   [API-1]       [API-2]
       \           /
        [ PostgreSQL ]
             |
        [ Replica ]
```

Не роби ASCII там, де вистачає списку. Список редагується, ASCII — ні.

## Супутник для тих, хто без VS Code

`.md` — **джерело**. Супутник — **вітрина** того самого змісту, де схеми нарешті виглядають
як схеми. Це конкретизація **правила C** канону (`skills/_shared/expert-standards.md`) для
навчальних курсів.

Бери перше, що доступне в поточному середовищі:

| Варіант | Де працює | Що дає |
|---|---|---|
| **Artifact / Claude Design** | Claude: застосунок, Code, веб | сторінка або канвас з артбордами за посиланням; відкриється з телефона, нікуди не треба носити файл |
| **Canvas** | ChatGPT, Gemini | редагований документ поруч із чатом; учень може правити сам |
| **HTML-файл поруч** *(універсальний дефолт)* | будь-де | подвійний клік → браузер, працює офлайн, схеми справжні, `Ctrl+F` шукає |
| **PDF** | будь-де | не зміниться, друкується, зручно на планшеті |

**Якщо не знаєш, що доступно** — не гадай і не пробуй навмання. Або спитай одним рядком,
або одразу роби HTML: він працює скрізь і нічого не вимагає від хоста.

**Як робити HTML:** самодостатній файл поруч із курсом —
`<category>/<topic>/<topic>.html`. Один файл, стилі всередині, без зовнішніх залежностей.

**Як робити PDF:** не винаходь пайплайн — він уже описаний і перевірений у
`skills/learning-retro/references/pdf_generation.md` (headless Chrome, друк HTML у PDF,
офлайн, без інсталяцій). Роби HTML → друкуй його.

**Коли пропонувати:** після того, як файли створені й учень підтвердив, що структура ок.
Одним рядком, без нав'язування:

> «Файли готові. Зробити ще візуальну версію зі схемами — відкриється з будь-якого пристрою
> і виглядатиме зрозуміліше за текст?»

Назви конкретний варіант, який тут доступний («сторінку», «канвас», «HTML-файл»), а не
абстрактне «візуалізацію». Учень має розуміти, що саме отримає.

### Жорсткі правила супутника

1. **Файл первинний.** Супутник генерується **з `.md`**, ніколи навпаки. Матеріал змінився —
   перегенеруй супутник, не прав його окремо. Інакше дві версії правди.
2. **Не заміна.** Курс має бути повністю зрозумілим без супутника. Він додає вигляд,
   а не зміст. Інші скіли (`anki-cards`, `recall-quiz`, `course-audit`) читають **`.md`**.
3. **Деградація.** Немає браузера для PDF, недоступний інструмент публікації — **пропусти
   мовчки**. Це не помилка й не привід попереджати. HTML усе одно лежить і відкриється.
4. **Без нав'язування.** Запропонував один раз, отримав «ні» — більше не повертайся в цій сесії.
5. **Схеми — тут.** Саме в супутнику доречні справжні діаграми, бо там вони гарантовано
   відрендеряться. У `.md` для не-VS-Code — списки й таблиці за патернами вище.

### Навчальні матеріали не йдуть у git

Згенеровані курси, плани, логи й супутники — **особисті файли учня**, не код. Якщо робоча
тека під git — переконайся, що в `.gitignore` є принаймні:

```gitignore
# навчальні матеріали — особисті, не для репозиторію
*_plan.md
*_learn.md
*_log.md
retro/
**/anki/

# чернетки: помилки, ідеї, проби
errors/
**/errors/
mistakes/
**/mistakes/
ideas/
**/ideas/
drafts/
**/drafts/
scratch/
**/scratch/
sandbox/
**/sandbox/
experiments/
**/experiments/
playground/
**/playground/
tmp/
**/tmp/
```

Якщо `.gitignore` немає або цих рядків у ньому немає — **скажи учню один раз** і запропонуй
додати. Не додавай сам без дозволу: це його репозиторій.
