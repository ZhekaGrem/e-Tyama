# lang_go — як Go читає код

Go компілюється в машинний код, без рантайм-VM на кшталт Node.js чи JVM. Немає класів —
є `struct` + методи з receiver'ом і embedding замість наслідування. Немає винятків у
звичайному потоці — помилка це значення типу `error`, яке повертають і перевіряють
`if err != nil`. Конкурентність — goroutine (`go`) і канали (`chan`, `<-`) — у цьому гайді
трактуються як `syntax_sugar` kind `async`, бо це мовна конструкція, а не бібліотечний виклик.
Експорт — не ключове слово, а регістр першої літери імені (деталі в §1).

## 1. Маркери

| kind | сигнал у коді | type |
|---|---|---|
| `const` | `^\s*const\b` | data |
| `let` | `^\s*var\b`, `:=` (коротке оголошення) | data |
| `literal` | число, рядок у `"..."`/`` `...` ``, `true/false/nil`, `[]T{...}`, `map[K]V{...}`, `T{...}` (композитний літерал) | data |
| `function` | `^func\s+\w+` (без receiver) | operation |
| `method` | `^func\s+\(\w+\s+\*?\w+\)` (з receiver) | operation |
| `operator` | `+ - * / % == != < > && \|\| =` | operation |
| `return` | `return\b` | operation |
| `if` | `if\b`, `switch\b`, `select\b` | operation |
| `loop` | `for\b`, `range\b` | operation |
| `async` | `go\b`, `chan\b`, `<-` | syntax_sugar |
| `decorator` | `defer\b` | syntax_sugar |
| `destructuring` | `a, b := f()`, `v, ok := m[k]` | syntax_sugar |
| `lambda` | `func(...)` як значення (анонімна функція — аргумент або присвоєння) | syntax_sugar |
| `import` | `^import\b` або блок `import (` | structure |
| `class` | `type \w+ struct` | structure |
| `interface` | `type \w+ interface` | structure |
| `type` | інші `type X Y` (alias або defined type) | structure |
| `export` | ідентифікатор (функція, тип, змінна, поле) з великої літери | structure |

Примітка до `export`: у Go немає ключового слова `export`. Видимість за межами пакета
визначає **регістр першої літери імені** — велика літера означає «видно ззовні», мала —
«приватне для пакета». Це властивість самого імені, а не окремого рядка коду.

## 2. Пастки читання

### 2.1 `init()` виконується після змінних пакета, до `main()`

```go
var cfg = load()

func init() { fmt.Println("init") }

func main() { fmt.Println("main") }
```

Порядок: ① `load()` — ініціалізація змінних пакета в порядку залежностей → ② всі `init()`
пакета, у порядку появи в джерелі → ③ `main()`.
Чому: спека описує ініціалізацію пакета як дві послідовні фази — спершу всі
package-level змінні за графом залежностей, потім виклик усіх `init()`; програма стартує,
викликаючи `main()` лише після того, як усі імпортовані пакети (і поточний) уже
проініціалізовані.
reading: STRUCTURE-елемент `init` — виняток, він **отримує order** у списку кроків (звичайні
`func`/`type`/`import` у STRUCTURE його не отримують).
Джерело: Spec, Package initialization.

### 2.2 `defer` — аргументи обчислюються зараз, виклик — потім, LIFO

```go
func f() {
    x := 1
    defer fmt.Println("a", x)
    defer fmt.Println("b")
    x = 2
}   // виводить: b, потім a 1
```

Порядок: f1 `x := 1` → f2 рядок `defer fmt.Println("a", x)`: аргумент `x` (=1) обчислено
й збережено зараз, сам виклик відкладено → f3 рядок `defer fmt.Println("b")`: зареєстровано
→ f4 `x = 2` → f5 вихід з `f`: відкладені виклики виконуються у зворотному порядку —
спершу `b`, потім `a 1`.
Чому: спека прямо каже — при виконанні `defer` значення функції та аргументи обчислюються
й зберігаються одразу, а сам виклик відбувається безпосередньо перед поверненням з функції,
у порядку, зворотному до реєстрації.
reading для `defer`: «аргументи зафіксовано тут; виклик — при виході з функції, у зворотному
порядку реєстрації».
Джерело: Spec, Defer statements.

### 2.3 Zero values — `var` без значення не порожній, а нульовий

```go
var n int              // 0
var s string            // ""
var p *T                // nil
var m map[string]int    // nil: читати можна, писати — panic
```

reading для `var m map[string]int`: «nil-map: читання за ключем дає нульове значення,
але запис у nil-map панікує; потрібен `make(map[string]int)`».
Чому: спека визначає, що змінна без явного ініціалізатора отримує zero value свого типу —
`false` для bool, `0` для чисел, `""` для рядків і `nil` для вказівників, функцій,
інтерфейсів, слайсів, каналів і мап.
Джерело: Spec, The zero value.

### 2.4 `:=` у вкладеному блоці — нова змінна, затінює зовнішню

```go
err := f()
if true {
    err := g()   // нова змінна цього блоку, зовнішня err не змінилась
    _ = err
}
```

reading: «`:=` усередині вкладеного блоку оголошує нове ім'я `err`; зовнішнє `err` лишається
старим значенням».
Чому: ідентифікатор, оголошений у блоці, може бути переоголошений у вкладеному блоці — поки
діє внутрішнє оголошення, ім'я позначає саме його, а не зовнішнє.
Джерело: Spec, Short variable declarations (та Declarations and scope, на яку спирається
правило затінення).

### 2.5 `go f()` не чекає на завершення

```go
go work()
fmt.Println("done")   // майже завжди виконується раніше за work()
```

Порядок: f1 `go work()` — функцію та аргументи обчислено в поточній goroutine, запущено нову
goroutine → f2 `fmt.Println("done")` виконується одразу, не чекаючи → work() виконується
«колись» у своїй goroutine.
Чому: спека каже прямо — виконання програми не чекає завершення викликаної функції; вона
продовжує виконуватись незалежно в новій goroutine.
reading: «запуск асинхронний; щоб дочекатись результату — потрібен `chan` або
`sync.WaitGroup`, самого `go` для цього недостатньо».
Джерело: Spec, Go statements.

**Додатково, без окремого номера:**

- **Порядок обчислення в межах виразу — зліва направо, але `&&`/`||` коротко замикають.**
  Виклики функцій/методів, receive-операції каналу (`<-ch`) і бінарні логічні операції в
  межах одного виразу, присвоєння чи `return` обчислюються в лексичному порядку зліва
  направо — **якщо взагалі виконуються**: правий операнд `&&`/`||` може не виконатись зовсім.
  У власному прикладі спеки `g(z || h(), i()+x[j()], <-c), k()` виклик `h()` відбувається,
  лише якщо `z` хибне — це коротке замикання, а не порушення порядку. Порядок обчислення
  інших підвиразів (наприклад індексів) спекою не гарантується.
  Джерело: Spec, Order of evaluation.
- **`if err != nil` — не цукор, а звичайний OPERATION kind `if`.** `error` — предекларований
  інтерфейс (`type error interface { Error() string }`), `nil` означає «помилки немає» за
  конвенцією мови; сама перевірка — звичайне порівняння значення, без особливого механізму
  на кшталт винятків.
  Джерело: Spec, Errors.

## 3. Список цукру

| конструкція | kind | equivalent | language_specific |
|---|---|---|---|
| `v, ok := m[k]` | destructuring | два значення з однієї індексації мапи: `v` — елемент за ключем (нульове значення типу, якщо ключа нема), `ok` — `bool`, чи ключ був присутній | так |
| `a, b := f()` | destructuring | послідовне присвоєння кожного значення, яке повертає `f()`, за позицією | так |
| `func(x int) int { return x*x }` як аргумент | lambda | іменована функція, оголошена окремо та передана за іменем | так |
| `defer f(x)` | decorator | явний виклик `f(x)` (з `x`, зафіксованим у момент `defer`) у кожній точці виходу з функції — `return`, кінець тіла, `panic` — у зворотному порядку реєстрації; аналог `try/finally`, але прив'язаний до виходу з функції цілком, а не до блоку | так |
| `go f()` | async | запуск `f()` як окремої goroutine; без прямого коду-еквівалента — мовний примітив конкурентності | так |
| `ch <- v` | async | send-операція каналу: записує `v` у `ch`, блокує поточну goroutine, доки приймач не готовий (для небуферизованого каналу) | так |
| `<-ch` | async | receive-операція каналу: читає з `ch`, блокує, доки хтось не надішле значення (для небуферизованого каналу) | так |

Виглядає як цукор, але ним **не є** — записувати як звичайні kind, не як syntax_sugar:

- **`for i := range xs`** — це `loop` (operation), а не окрема цукрова форма: `range` тут
  просто джерело значень для звичайного циклу `for`.
- **`x.(T)` (type assertion)** — це `operation` kind `if`, не `optional_chaining`: перевірка
  типу в рантаймі, з можливим другим значенням `ok` (`v, ok := x.(T)`) — сама перевірка
  панікує без `ok` і не «пробирається» крізь `nil` мовчки, як `?.` у JS.
- **`T{A: 1}` (композитний літерал структури)** — це `literal` (data), звичайне значення,
  а не деструктуризація чи spread.
- **`struct { Base }` (вбудовування)** — це `structure` kind `class`, з приміткою
  «embedding, не наслідування»: методи `Base` стають доступні через зовнішній тип, але
  це композиція полів, не ієрархія класів.

## 4. Side effects — як розпізнати

- **I/O:** `fmt.Print*`, `log.*`, `os.*` (файли, середовище, `os.Exit`), `net/http.*`,
  `io.*` (Reader/Writer), будь-який виклик методу `sql.DB`/`sql.Rows`.
- **Глобальний стан:** присвоєння змінній, оголошеній на рівні пакета; `sync.Once.Do(...)`;
  сам факт наявності `init()` у пакеті (він завжди виконується побічно, до `main`).
- **Мутація аргументу:** будь-який метод із receiver `*T`, що пише в поля; `append` до
  слайсу, переданого як параметр (може змінити спільний бекінг-масив, якщо є запас
  ємності); запис за ключем у мапу, передану як параметр — мапа завжди передається як
  посилання на одну й ту саму структуру даних.

Функція з будь-чим із цього → `side_effect: "<що саме>"`, у гайді ⚠️ і червона рамка.

## 5. Entry point

1. `func main()` у файлі з `package main`.
2. `cmd/<name>/main.go` — стандартне розташування точки входу в багатомодульних Go-проєктах.
3. `main.go` у корені репозиторію.
